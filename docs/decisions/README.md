# 决策记录（decisions）

本目录存放**设计决策与排查结论**，回答「为什么是这样」（Why），对应 `docs/` 其余部分回答「是什么」。

## 为什么会有这个目录

仓库此前**没有任何决策记录**。一个具体后果：`app/core/security.py:81` 那句
「必须先从数据库 reload 一下，确保 `is_superuser` 状态是最新的」——
`git log -S` 显示它自 **2026-04-29 初始提交**就存在，**没有记录任何理由**，
也没有 ADR 目录、设计文档或讨论记录可供追溯。到 2026-09 排查认证边界时，
只能靠代码反推意图。

这个目录是为了不再重复这件事。

## 与 git 历史的分工

- **git commit / PR** 回答「改了什么」——适合代码级、自解释的改动。
- **本目录**回答「为什么这么选、当时考虑过什么、哪些方案被否决了、哪些结论是推导而非实测」——
  这些在 commit message 里会被压扁，在 issue 里会被时间线冲散。

## 写法要求（给后来者）

一份好的决策记录应当包含：

1. **结论**（放在最前，不要让人读到最后才知道选了什么）
2. **被否决的方案及否决理由**——这往往比结论本身更有价值
3. **依据**：规范原文 / 实测数据 / 代码证据，注明出处
4. **明确区分「实测」与「推导」**——推导的结论要写出推导链条，并说明它的前提在哪
5. **已知的不确定项**——写清楚哪些没验证，比假装都验证过更有用

> 反面例子见第一份文档的修订痕迹：它最初把「Redis 缓存 + 用户已从 DB 删除」
> 写成「最重要」的可达路径，后来实测发现该服务只做**软删除**（`users.py:903-904`
> 只设 `is_active = False`），该路径需要绕过 API 的手工硬删。**结论没变，但严重性
> 判断错了**——文档里保留了这次修正，而不是抹掉。
